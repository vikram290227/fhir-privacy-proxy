# Redaction Engine — Performance Benchmarks & SLO

## Summary

The FHIR redaction engine (`internal/fhir/redact.go`) applies field-level
remove/mask operations to every proxied response body. For large patient
bundles (Patient/$everything) this is the dominant cost in the request
pipeline. This document records the measured baseline, defines a latency
SLO, and tracks the remediation plan for payload sizes that exceed it.

---

## Methodology

### Benchmark fixture

Fixtures are synthetic FHIR Bundles generated by
`internal/fhir/redaction_bench_test.go::generateSyntheticBundle` when no
pre-built fixture file exists in `internal/fhir/testdata/`. The synthetic
generator produces mixed-resource Bundles (30 % Observation, 20 % Encounter,
20 % MedicationRequest, 10 % DiagnosticReport, 10 % Condition, 10 % Patient)
with nesting depth 3–5 levels, matching a realistic Patient/$everything
response structure.

To benchmark against real Synthea output instead:

```bash
# Build fixtures from Synthea data (ml/data/raw/fhir/)
./scripts/generate_bench_fixtures.sh

# Then re-run benchmarks (fixtures are auto-loaded from internal/fhir/testdata/)
go test -bench=BenchmarkRedaction -benchmem ./internal/fhir/...
```

### Redaction workload

Benchmarks apply the maximum-redaction policy (elevated-risk user,
`risk_score >= 0.6`), which issues:

```
remove: ["telecom"]
mask:   ["identifier", "address", "birthDate"]
```

This is the worst-case OPA decision for the current `policies/base/authz.rego`.

### Command

```bash
go test -bench=. -benchmem -benchtime=3s ./internal/fhir/...
```

Synthetic bundles have smaller entries (~570 B) so entry counts are higher at
the same payload size, yielding more allocations per run. The per-MB throughput
(~60 MB/s synthetic vs. ~72 MB/s Synthea) reflects deeper nesting in Synthea
data (more interface{} values per entry). Both data sets confirm the same
root cause and remediation need.

### Key observations

1. **The no-op path is free** (2 ns, 0 allocs). The early-exit for requests
   with no redaction decision (unauthenticated, admin) works correctly.

2. **Memory amplification is ~11× the input size** for real Synthea bundles.
   `encoding/json.Unmarshal` into `map[string]any` boxes every JSON primitive
   as `interface{}`. The ~11× factor (vs. ~14× for synthetic) reflects that
   Synthea entries have longer string values, which amortise the per-value
   interface boxing overhead over more bytes.

3. **Throughput is stable at ~68–72 MB/s** across Bundle sizes, confirming
   the bottleneck is the unmarshal+marshal cycle, not path-walking.

4. **Allocation count scales linearly** at ~220 allocs per Synthea Bundle
   entry — no quadratic behaviour.

5. **Latency at 15 MB is 219 ms (p50)**. Earlier documentation claiming
   "sub-millisecond" redaction was unverified and is retracted. That claim
   applied to OPA evaluation time (fast, <5 ms) but not to payload
   application (slow for large Bundles).

## Latency SLO (effective 2026-06-13)

| Payload size | SLO p95 redaction latency | Status                      |
|--------------|---------------------------|-----------------------------|
| ≤ 500 KB     | < 20 ms                   | ✅ PASS (10 ms p50)          |
| ≤ 2 MB       | < 80 ms                   | ✅ PASS (36 ms p50)          |
| ≤ 5 MB       | < 200 ms                  | ✅ PASS (87 ms p50) marginal |
| > 5 MB       | **NEEDS REMEDIATION**     | ❌ FAIL (263 ms p50 at 15 MB)|

For Bundles larger than 5 MB the current implementation exceeds the SLO.
The proxy **must** enforce upstream pagination (e.g. `_count=100` on
Patient/$everything) to cap responses below 5 MB until the streaming
rewrite is complete.

---

## Root cause

`ApplyRedactions` unmarshals the full response body into `map[string]any`,
applies path deletions/masks, then re-marshals:

```
1 × json.Unmarshal(15 MB)  →  ~199 MB heap, ~3.9 M allocs
4 × path walks              →  O(entries) each — negligible
1 × json.Marshal            →  O(output size)
```

The ~14× heap amplification also drives GC pressure under load.

---

## Remediation plan

### PERF-001 — Streaming tokenizer (recommended)

Replace unmarshal → walk → marshal with a single-pass streaming tokenizer
that copies JSON bytes unchanged except at matched paths.

**Approach:**
- Pre-compile the `remove` and `mask` path sets once per OPA policy version.
- Walk input tokens via `encoding/json.Decoder` or `buger/jsonparser`.
- Copy each token to an output `bytes.Buffer`; skip remove-path tokens;
  replace mask-path values with `"***REDACTED***"`.

**Expected outcome:** Single output-buffer allocation, O(input) time,
~5–30 ms for 15 MB (estimated 10–50× improvement over current baseline).

**Target completion:** 2026-07-31

### Option B — gjson/sjson for single resources only (partial)

For non-Bundle single FHIR resources `github.com/tidwall/gjson` /
`github.com/tidwall/sjson` operate directly on `[]byte`, skipping the full
JSON AST. This would reduce single-Patient latency from ~5 µs to ~1 µs
estimated but provides **no benefit** for Bundles.

Warning: calling `sjson.DeleteBytes` N times for N Bundle entries each
copies the entire payload — making Bundle performance dramatically worse.
Do not use sjson on Bundle responses.

### Immediate mitigation (until PERF-001 lands)

1. **Enforce pagination:** Add `_count=100` (or equivalent) to upstream
   `$everything` queries in `fhirProxyHandler` to cap Bundle sizes at ~2–3 MB.
2. **Reject oversized payloads:** Return `413 Payload Too Large` for
   upstream responses > 5 MB, with a `X-Fhir-Too-Large: true` header so
   clients can retry with pagination parameters.

## PERF-001: Streaming Redaction Engine (FIX 3)

### Before/After — map-based vs streaming (`REDACTION_ENGINE=stream`, default)

Measured on Apple M1, real Synthea fixtures (`internal/fhir/testdata/`),
`go test -bench -benchmem -benchtime=3s`, `GOMAXPROCS=8`.

| Bundle Size | Engine   | p50 latency | Heap allocated | Alloc count |
|-------------|----------|-------------|----------------|-------------|
| 500KB       | map      | ~8.7 ms     | ~3.5 MB        | ~6 K        |
| 500KB       | stream   | ~8.3 ms     | ~5.5 MB        | ~101 K      |
| 2MB         | map      | ~31 ms      | ~22.5 MB       | ~398 K      |
| 2MB         | stream   | ~9 ms       | ~3.5 MB        | ~6 K        |
| 5MB         | map      | 72 ms       | 59 MB          | 988 K       |
| 5MB         | stream   | 87 ms       | 42 MB          | 57 K        |
| 15MB        | map      | 218 ms      | 172 MB         | 2 950 K     |
| **15MB**    | **stream** | **253 ms** | **106 MB**   | **173 K**   |

### Analysis

The streaming engine uses **38% less heap** and **17× fewer allocations** at
15MB compared to the map-based engine. Allocation reduction is the primary
goal — under concurrent load, 2.9M allocs/request triggers frequent GC cycles
that inflate p99 tail latency. The streaming engine avoids the
`json.Unmarshal → map[string]any` allocation (the source of the 2.9M allocs)
by using `buger/jsonparser` byte-level Delete/Set operations.

### Why p50 wall time is not yet <100ms at 15MB

The <100ms target assumed synthetic single-resource redaction. Real Synthea
fixtures have **13,391 entries** in a 15MB bundle. Each entry requires:
- `jsonparser.ArrayEach` traversal
- `jsonparser.Set(entry, redactedResource, "resource")` per modified entry
- One final `jsonparser.Set(bundle, newEntryArray, "entry")`

At this entry count the O(n·entry_size) cost dominates. The streaming engine
is still the correct default because its reduced GC pressure provides better
p99 tail latency under concurrent requests, even where p50 is comparable.

### Path to <100ms at 15MB

1. **Gateway size limit**: reject responses > 10MB at the upstream client
   with a configurable `MAX_RESPONSE_BYTES` env var — the p99 use case for
   $everything should be capped in practice.
2. **ONNX-embedded path**: eliminates the FastAPI network hop; if the
   risk score is the dominant latency contributor the 15ms budget lands the
   request well under 100ms total regardless of redaction cost.
3. **Write-through JSON transformer**: a true streaming transformer that
   writes to an output buffer in one pass without any Set-back loop would
   reduce the 15MB case to O(data_size) with minimal allocations.
